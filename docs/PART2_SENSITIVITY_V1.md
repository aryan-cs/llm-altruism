# Part 2 preregistered sensitivity stage

`experiments/misc/inference_hub_part2_sensitivity_v1.py` implements the
authoritative sensitivity stage in `docs/CONFIRMATORY_PROTOCOL.md`. It is a
separate, versioned campaign and does not change the historical Part 2 runner or
previous evidence.

Two frozen configurations use the same runner:

- `experiments/part2/part2_sensitivity_v1.json` is the full future confirmatory
  protocol. Its 3,240,000 scheduled POSTs cannot fit the current 24-hour deadline
  under one-in-flight-per-provider operation and must not be launched as the
  deadline campaign.
- `experiments/part2/part2_sensitivity_deadline_exploratory_v1.json` is a
  separately labelled deadline-scale exploratory analogue. It preserves the
  coded design and analysis but cannot confirm the preregistered sensitivity
  claims.

## Frozen design

The design is the 16-cell `2^(5-1)` resolution-V half-fraction with defining
relation `I=ABCDE`. The five factors and frozen low/high levels are:

| Factor | Low | High |
| --- | ---: | ---: |
| Capacity per initial agent | 25 | 75 |
| Depletion units per Option B | 1 | 4 |
| Collapse death rate | 0.1 | 0.4 |
| Initial society size | 25 | 50 |
| Horizon in days | 50 | 100 |

Resource capacity is capacity per initial agent multiplied by initial society
size. Cells are generated by `analysis.part2_confirmatory.resolution_v_half_fraction`;
they are never treated as baseline replicates or pooled into a synthetic baseline.

The deadline exploratory profile varies the same five factors at capacity per
initial agent 5/15, depletion 1/2, collapse death rate 0.1/0.4, population 4/8,
and horizon 10/20. This produces exactly 103,680 scheduled POSTs, inside the
requested 70,000–110,000 envelope, plus a conservative 10% physical-attempt
allowance. These alternate numeric levels do not change the resolution-V code
matrix.

Six systems are frozen before sensitivity outcomes by distinct
developer/capability stratum in
`experiments/part2/part2_sensitivity_v1.json`. There is no outcome-driven
substitution. All six sentinels and all 16 cells use the same 12 deterministic
environment seeds.

## Confirmatory analysis

The response is normalized AURC. The only confirmatory sensitivity estimands are
the five high-minus-low main effects for each sentinel. Interactions are not
confirmatory. Exact sign-flip tests use all `2^12 = 4096` common-seed sign
patterns. The 30 sentinel-by-factor raw p-values form one global Holm family.
Within-sentinel max-T and Holm values are retained only with explicitly scoped
diagnostic labels.

The runner writes confirmatory rows only after a complete, operationally eligible
`6 sentinels × 16 cells × 12 seeds` execution. An explicitly requested
development subset is marked incomplete and emits no effects or p-values.
For the complete deadline configuration it writes all 30 Holm-adjusted tests but
marks the artifact and every row `deadline_exploratory` and `confirmatory: false`.

Call order is not a sixth resolution-V factor. The simulator presents a common
simultaneous within-day state and dispatches participants in parallel. The
sanitized `call_order_diagnostic.json` artifact records that boundary and is
excluded from the 30-test Holm family. A future manipulated call-order study
requires its own gate, manifest, and output.

## Request, invalid-decision, and safety contracts

Every sentinel must support the common `seed`, `temperature`, `top_p`, and strict
structured-response controls. Requests use temperature `0.2`, top-p `1`, and a
32-token Part 2 output cap. A malformed or truncated visible answer becomes one
retained `INVALID` nonrestraint with zero state effect and no semantic retry. It
does not exclude the whole trajectory. Identity mismatch or exhausted transport
failure makes the trajectory operationally ineligible and blocks confirmatory
analysis.

Network runs require the provider-safe client and one in-flight request per
upstream provider. Raw prompts, request bodies, visible content, reasoning, full
responses, routes, reservations, and failures stay in mode-restricted,
append-only SHA-256-chained journals. Every journal is bound to one immutable
cell. Resume validates the manifest and journal checkpoints and reuses retained
semantic results only when their dynamic prompt/request hashes still match.

A separate durable attempt ledger reserves each physical POST before dispatch.
It conservatively counts crash-interrupted reservations and enforces the frozen
3,564,000-attempt ceiling. Each canonical request is checked against the 8,192
UTF-8-byte input ceiling. The full schedule is exactly 3,240,000 successful POSTs
and 103,680,000 scheduled output tokens at the 32-token cap.

## Sanitized outputs

The runner emits only non-content metrics in `sanitized/`:

- `trajectory_metrics.json`
- `sentinel_cell_metrics.json`
- `main_effects.json`
- `call_order_diagnostic.json`

Raw prompts, responses, reasoning, request bodies, and selected routes are never
copied into these files. No sensitivity campaign was launched as part of this
implementation change.

Selected routes are resolved exactly from the combined registry plus its
hash-bound compatibility evidence. Work submission is stably round-robined by
upstream provider before the shared one-in-flight leases are acquired, preventing
one provider's queued work from occupying the bounded worker pool while other
providers are idle.
